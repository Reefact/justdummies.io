# ADR-0011 | The playground references the catalogue as a project reference

🌍 🇬🇧 English (this file) · 🇫🇷 [Français](0011-le-playground-reference-le-catalogue-comme-un-project-reference-fr.md)

**Status:** Accepted
**Proposed:** 2026-08-15
**Accepted:** 2026-08-15
**Decision Makers:** Reefact

## Context

`Directory.Packages.props`, entry B2 in `docs/design/decisions-inventory.md`, and the JustDummies
package reference in `apps/playground`'s own project file all state the same rule: **the playground
references a published NuGet package of the library it demonstrates, never a source build of it.**
The reasoning is stated in `Directory.Packages.props` itself — this repository is deliberately
separate from the library's precisely so that a project reference to the library is not even
possible, because a playground running the library's `main` would offer constraints that exist in
no shipped package, and a visitor would find them missing minutes after installing.

ADR-0010 introduces `packages/playground-catalogue`, a new project generated by
`tools/playground-catalogue` (which itself references `JustDummies` the normal, package-pinned
way) and consumed by `apps/playground` via `<ProjectReference>` — a `ProjectReference`, in the same
solution, to something that is not published as a NuGet package.

Read only by its shape, this looks identical to the thing B2 forbids: `apps/playground` gaining a
`ProjectReference` to code it did not install as a package.

## Decision

**`apps/playground`'s `ProjectReference` to `packages/playground-catalogue` does not reopen B2.**
`packages/playground-catalogue` is site-owned generated glue that itself depends on `JustDummies`
the ordinary, package-pinned way (via `tools/playground-catalogue`'s own `PackageReference`) — it
is not, and never becomes, a substitute for installing the library.

## Rationale

B2's actual concern is what the playground *demonstrates*: a constraint or generator visible in
the playground must exist in the shipped package a visitor is about to install, which fails the
moment the playground can reach code the package does not carry. A `ProjectReference` from
`apps/playground` to the *library itself* would do exactly that — the playground would run
whatever is on `main`, not what is published, and the two would drift apart silently.

`packages/playground-catalogue` carries no library code of its own. Its two generated files
(`PlaygroundCatalogue.Descriptors.g.cs`, `PlaygroundCatalogue.Dispatch.g.cs`) are produced by
reflecting over the very same package-pinned `JustDummies` assembly `apps/playground` itself
references — the generator's own `PackageReference Include="JustDummies"` carries no local
`Version`, so it resolves from the identical central pin in `Directory.Packages.props` as every
other consumer in this repository. Nothing about this path lets `apps/playground` reach a
constraint the shipped package does not have: what the generated dispatch table can call is
bounded exactly by what that pinned package's assembly exposes.

The dependency this ADR clarifies is therefore orthogonal to B2's, not a variant of it:
`apps/playground` → `packages/playground-catalogue` → (`PackageReference`) → `JustDummies`. The
library is still reached through exactly one path, the package, and B2's guarantee — the
playground never offers a constraint the shipped package lacks — holds regardless of how many
site-owned intermediate projects sit between `apps/playground` and its own `Program.cs`.

## Alternatives Considered

### Fold the generated files directly into `apps/playground`, no separate project

Considered because it removes the `ProjectReference` entirely, which would make this ADR
unnecessary — nothing to clarify if there is only one project.

Rejected on its own terms, independent of B2: `tools/playground-catalogue` (the generator) already
needs the descriptor/dispatch record shapes and `ArgumentParsing` to emit against, and a generator
project cannot depend on the Blazor WebAssembly application it generates code *for* — that would be
circular (the generator would need `apps/playground` to build, and `apps/playground` needs the
generator's output to build). A separate, dependency-light project both the generator and the
playground can reference is what breaks the cycle; folding the files into `apps/playground` alone
reintroduces it.

### Publish `packages/playground-catalogue` as its own NuGet package, referenced like `JustDummies` is

Considered because it would make every dependency in the solution look the same — everything a
`PackageReference`, nothing a bare `ProjectReference` — arguably a more disciplined uniformity than
this decision settles for.

Rejected as solving a problem B2 does not have. B2's guarantee is about the *library*
(`JustDummies`) never being reached except through what is shipped to visitors; it says nothing
about site-owned build tooling needing the same treatment. Packaging and versioning a project that
is regenerated on every build, never consumed outside this repository, and never meant to be
installed by anyone would add real process (a release cadence, a version number, a feed) to answer
a concern that does not apply to it.

## Consequences

### Positive

* B2's guarantee is unaffected: the library is still reached through exactly one path, the pinned
  NuGet package, from every project in the solution that touches it.
* The generator and the playground share one set of types
  (`MemberDescriptor`, `ChainStep`, `ChainResult`, `ArgumentParsing`) without either needing to
  depend on the other.

### Negative

* A future contributor scanning `apps/playground`'s project references for "does this reach outside
  a published package" needs this ADR (or the reasoning it records) to tell the two
  `ProjectReference`-shaped situations apart — the shape alone does not.

### Risks

* If `packages/playground-catalogue` ever grows logic that does not derive from the pinned
  `JustDummies` assembly — hand-written business logic unrelated to the catalogue, say — this
  decision's reasoning would no longer hold and would need revisiting. Nothing in the current
  codebase does this; it is named here as the condition that would reopen the question.
